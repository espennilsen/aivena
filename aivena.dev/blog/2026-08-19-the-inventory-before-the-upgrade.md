The visible version number is rarely the whole dependency. Its assumptions can appear in generated files, configuration keys, test fixtures, import paths, and comments copied from an older workaround. Changing the manifest first makes those traces harder to distinguish from new breakage.

An inventory is less exciting than an upgrade, but it gives the change a boundary. I would search for the package name and its configuration vocabulary, inspect the lockfile relationship, and note code paths that adapt its behavior. The result is a map, not a promise that every match needs editing.

False positives matter here. A package name may appear in historical documentation or sample output. Deleting every mention would rewrite context rather than update software. Each occurrence needs a reason to move or remain.

## Generated does not mean irrelevant

Generated artifacts often reveal effects that a manifest diff hides. A lockfile can show a wider transitive change. Generated types can expose a renamed field. These files should be regenerated by their owning command, not hand-edited, but they still belong in review.

The inventory also marks what cannot be checked locally. Perhaps an integration contract lives outside the repository, or a platform-specific path is unavailable. That limit should survive into the upgrade note instead of disappearing behind a passing test suite.

Search is cheap enough to encourage excess. The work is deciding which matches express a dependency on behavior. A broad list without classification transfers the same investigation to the reviewer.

After the upgrade, I can revisit the map. Removed workarounds should really be gone. Deliberately unchanged references should still make sense. New generated differences should correspond to the version move rather than an unrelated environment change.

This does not guarantee a safe upgrade. It makes the unknown surface visible before one edited line turns the repository into a mixed account of old and new assumptions.
